# Honest Voice - 組織の本音を引き出すプラットフォーム

## 1. サービス概要

### このサービスはどんなサービスか

**Honest Voice** は、組織内の「本音」を安全に集約し、経営層が真の課題を理解できるプラットフォームです。社員は完全に匿名で意見を述べることができ、統計分析と可視化がその場で行われます。

### 誰の、どんな課題を、どう解決するか

**ユーザー**: 企業の経営層・HR 責任者

**課題**: 
- 会議やアンケートでは「表向きの意見」しか出てこない
- 職位や人間関係の力学で、本当の課題や不満が隠れている
- 既存の匿名ツールは複雑で導入ハードルが高い、または本当に匿名なのか信用できない

**解決方法**:
- **完全匿名システム**: セッション ID のハッシュ化により、回答者を絶対に特定できない
- **シンプルな UI**: 誰でも簡単に質問を作成でき、結果はその場で統計表示
- **小規模から導入可能**: 個人・小規模企業でも手軽に利用できる価格・使いやすさ
- **改善サイクルの支援**: データを見た後、具体的な改善施策と報告までをサポート

**結果**: 
社員は「本当に聞いてくれる会社」という信頼を感じるようになり、経営層は「現実に基づいた意思決定」ができるようになります。組織全体が本音で語り合える文化が育まれます。

---

### このサービスが解決する本質的な問題

多くの企業は「心理的安全性が大切」と知っていますが、実装が難しいのが現状です。

Honest Voice は、以下の 3 つの要素を組み合わせることで、その実装を可能にします：

1. **技術的信頼**: 絶対に個人特定できない匿名の仕組み（セッション ID ハッシュ）
2. **操作的シンプルさ**: 複雑な設定がいらず、質問を作って、結果を見るだけ
3. **アクションへの繋がり**: 統計を見た後、組織としてどう変わるかまでサポート

これにより、「聞く場所」から「行動が変わる仕組み」へと進化させます。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

**シチュエーション**: 企業、組織における会議やアンケート

- **いつ**: 企業内での意思決定や改善施策の検討時
- **どんな状況で**: 上司や経営層が「全員の意見を聞きたい」と決定プロセスを開く場面
- **どんな気持ちか**: 社員から出てくるのは「表向きの意見」だけで、本当の課題や不満が表に出ていない。本音を言いにくい空気が組織にある

### 2-2. なぜそれが「気になった」のか

- **自分の価値観**: 組織の健全性は「メンバーが本音を言える環境」にあると信じている
- **過去の経験**: 匿名で聞いた意見と公開の場での意見のギャップを見てきた
- **問題意識**: 今の企業では心理的安全性の重要性は知られているが、実装が難しい

## 3. 課題の整理

### 3-1. 表に見えている困りごと

組織が「全員の意見を集めたい」と思っているのに、
- 職位や人間関係の力学が邪魔になり、本当の声が集まらない
- 既存のアンケートツールは「氏名記入」が標準で、匿名性確保が難しい
- 回答が紙やメールだと、集計・分析に手作業がかかる

### 3-2. 本当に解決したい課題

**なぜ困るのか（1回目）**
→ 意思決定が現実から遠ざかり、組織の改善がうまく進まない

**なぜ困るのか（2回目）**
→ メンバーの満足度や生産性が上がらず、離職につながるかもしれない

**なぜ困るのか（3回目）**
→ **組織が成長できず、個人も組織も本来のポテンシャルが発揮できない**

**本当に解決したい課題**: 
「**経営層とメンバーの間に『本音で語り合える場』を作り、組織が信頼に基づいて変わっていく体験**」

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

**Primary User: 経営層・管理職（Admin）**

年齢設定：
- 年齢: 30～50代
- 理由: 組織変革の責任と権限を持つ層。組織文化・心理的安全性に関心が高い

生活・状況設定:
- 生活・状況: 「社員から本音が聞きたいが、会議では本心が出ない」という課題に日々直面
- 理由: 匿名フィードバックにより、本当の課題を把握でき、的確な施策を打てる

環境設定:
- 環境: 中堅企業～大企業（50～1000名規模）
- 理由: 組織規模が大きいほど、階層の隔たりが大きく、匿名フィードバックの必要性が高い

**Secondary User: 社員（Employee）**

年齢設定:
- 年齢: 20～40代
- 理由: 心理的安全性に敏感で、本音で意見を述べたいニーズが高い世代

生活・状況設定:
- 生活・状況: 会社での意見や要望があるが、職位や人間関係で言いづらい状況
- 理由: 完全匿名なら「本音で話せる場」として使ってくれる

環境設定:
- 環境: 企業内（オフィス・リモート問わず）
- 理由: ブラウザアクセスで、どの環境からでも回答できる

### 4-2. 自分とユーザーの距離

選択: **身近な誰か**

理由: 
職場での「言いづらさ」や「本音と建前のギャップ」は、多くの職場人が経験している一般的な課題。自分も含め、周囲の同僚や先輩・後輩から「本当はこう思っているんだけど...」という話をよく聞いてきた。

### 4-3. 実際に使われる可能性について（需要・存在確認）

- **最初に使ってくれそうな人**: 組織改革に熱心な HR 責任者・経営層
- **思い出す場面**: 「組織課題を把握したい時期（四半期ごと、人事評価時期など）」
- **現在の代替手段**: 紙アンケート、Google Forms、Slack アンケート（ただし不完全な匿名性）
- **置き換える理由**: 「完全匿名 + 統計分析 + 定期的な実施」がワンストップで実現できる

**検証ポイント**: 
データが集まった後、ユーザーが「その後、どう行動するか」をサポートする機能が重要。
統計を見るだけでなく、「改善案を立てる → 実行する → 結果を報告する」というサイクルまでサポートできないと、使い続けてはもらえない。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ（導入・継続の流れ）

**きっかけ**:
- 「従業員満足度が下がっている」「退職者が増えている」などの危機感
- HR 責任者が「心理的安全性測定ツール」を探す
- OR 企業研修・コンサルが提案

**最初の一歩**:
1. 管理者登録（企業メール）
2. 最初の質問を作成し、社員に公開
3. 社員が登録・回答
4. 統計が可視化される

**続ける理由**:
- **習慣化**: 月 1 回の「声を聞く会」として定期実施
- **必要性**: CEO 月次施策の改善に使われる（フィードバックループが見える）
- **価値**: 社員から「ちゃんと聞いてくれる会社」という信頼が生まれる

**toB 固有の検討事項**:
- **導入判断の理由**: HR・経営層が「心理的安全性」「エンゲージメント向上」を重視する経営方針を持つこと
- **機密情報の信頼**: 「セッション ID ハッシュのみ記録で、絶対に個人特定ができない」という仕組みを明確に説明
- **既存ツール乗り換えのハードル**: 既存アンケート（Google Forms など）からの移行コストは低いが、「本当に匿名か？」という不信感を払拭する必要がある

## 5. 既存サービス・競合調査

### 5-1. 似たサービスの調査

**サービス名**: Wantedly, Glassdoor, 従業員満足度調査ツール（各社製品）

**URL**: glassdoor.com, 各企業 SaaS

**どんなことができるか**:
- 従業員の満足度・エンゲージメント測定
- 匿名アンケート機能
- グラフ化・分析機能
- 定期調査実施

### 5-2. それでも自分が作りたい理由

既存サービスの不満点:
- **高額**: 既存ツールは企業単位の契約が前提で、個人・小規模企業では手を出せない
- **複雑**: 設定が難しく、「とりあえず聞きたい」という軽い用途に向かない
- **ブラックボックス**: データがどう管理・保存されているか不透明
- **外部ツール依存**: IT 部門の許可が必要になりがち

**自分が欲しい体験**:
「会議の時間を取る感じで、誰でも簡単にアンケートを作成でき、結果を見て、次のアクションに繋げられる」

### 5-3. 差別化を一文で決める

**私のアプリの差別化ポイント**:
「**個人でも小規模企業でも導入でき、完全に匿名で、統計分析がその場でできる、シンプルで信頼できるフィードバックプラットフォーム**」

## 8. このアプリの懸念点とその対策

### 懸念点①: 導入企業が「本当に匿名か？」を信頼できるか

- **何が問題になりそうか**: 企業 HR が「本当に誰が答えたかわからないのか？」という疑いを持ち、導入をためらう
- **なぜそう思うか**: 個人開発のツールであり、ブラックボックスな部分が多いと見えるから。既存の大企業 SaaS には「セキュリティ監査済み」というお墨付きがある
- **そのために考えている対策**:
  - **仕組みの透明化**: 「セッション ID のハッシュのみ保存、元の ID は絶対に保存しない」を図で説明
  - **オープンソース化の検討**: ソースコード公開により、「本当に匿名か」を監査できる環境を整備
  - **第三者認証**: セキュリティ監査を受け、「個人情報処理基準クリア」という証拠を用意

### 懸念点②: 「一度聞いて終わり」になってしまう可能性

- **何が問題になりそうか**: Admin が統計を見て満足し、その後のアクション（改善施策）に結びつかない → 社員の「本音を聞いてくれた」という期待が裏切られる → 次期調査で回答率が下がる
- **なぜそう思うか**: 既存アンケートツールもこの課題を抱えており、データ分析は得意だが「その後どうするか」が欠けている
- **そのために考えている対策**:
  - **フォローアップ機能**: 統計を見た後、「改善案」「実行予定」「結果報告」をテンプレート化し、社員に共有できる仕組み
  - **定期質問のプリセット**: 「エンゲージメント」「組織文化」など、毎月・四半期ごとに追跡できる質問テンプレート
  - **改善サイクルのガイド**: 「voice → action → report」というループを実装し、習慣化を支援

### 懸念点③: 小規模企業・個人利用での回答数不足

- **何が問題になりそうか**: 社員数が少ない組織では「統計」として機能しない（5 名中 4 名が同じ意見だと、統計というより「多数派」になってしまい、匿名性の意味が薄れる）
- **なぜそう思うか**: 匿名性と統計的信頼性はトレード・オフ。サンプル数が少ないと、個人を特定しやすくなる
- **そのために考えている対策**:
  - **小規模向けモード**: 少数回答の場合は「グラフ非表示、テーブルのみ」「最小サンプル数の警告」
  - **定性情報の重視**: 統計ではなく「コメント・意見」そのものに価値を置く UI 設計
  - **複数組織横断比較**: B2B SaaS として発展させ、業界別・企業規模別の比較データを提供

## 9. 今後の展開・発展の方向性

このアプリは「一度聞いて終わり」にならないために、以下の広がりが考えられます。

### ユーザーの継続使用
- **なぜ続ける**: 定期的（月 1 回、四半期ごと）にアンケートを実施し、「組織が本当に変わっているか」を追跡する習慣
- **何が変わる**: 社員エンゲージメント向上 → 離職率低下 → 組織生産性向上

### データの蓄積
- **データが溜まると何ができるか**:
  - 「この時期はこんな課題が出る」という季節性の発見
  - 施策実行前後での意識変化の測定
  - 部門別・チーム別の課題パターン認識

### 他者との関わり
- **運用・仕組みで価値を出す**:
  - 「改善サイクル」を組織文化として定着させる支援
  - HR コンサルティングとの連携（統計データを基にした改善提案）
  - ベストプラクティス共有コミュニティ（「こういう課題にはこう対応した」）

### 発展案

**機能追加の方向性**:
- 複数組織横断分析（業界別ベンチマーク）
- AI による自動テーマ抽出（回答コメントの自然言語処理）
- Slack / Teams との連携（チーム内での共有・通知）
- フリマーケットプレイス型の「質問テンプレート」販売

**UI・体験の改善**:
- ダッシュボードの改善（わかりやすい統計表示）
- モバイルアプリ化
- リアルタイム投票・即時結果表示

**機能以外の工夫**:
- 無料トライアル・サブスクリプション体系
- 実装サポート・研修パッケージ
- データセキュリティの第三者認証取得

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

- **フレームワーク**: Rails 7.x
- **フロントエンド**: React (react-rails gem)
- **ビルドツール**: esbuild
- **CSS**: Tailwind CSS + DaisyUI
- **認証**: Devise
- **DB**: SQLite3 (開発) / PostgreSQL (本番)
- **グラフ**: Chartkick + Chart.js
- **テスト**: RSpec + FactoryBot

### 10-2. 技術選定の理由

| 技術 | 選定理由 | チャレンジ点 |
|------|---------|-----------|
| Rails 7 | MVC 構造が明確、成熟フレームワーク | 大規模スケーリング時のチューニング |
| React | インタラクティブな UI、コンポーネント再利用性 | 学習コスト、状態管理の複雑性 |
| esbuild | 高速ビルド、Rails デフォルト対応 | Webpack との違いを理解することが必要だが、実務的には問題なし |
| Tailwind + DaisyUI | 開発速度 UP、モダン UI | カスタマイズ時の制限 |
| PostgreSQL | スケーラビリティ、本番環境対応 | ローカル開発環境の準備 |

### 10-3. キャッチアップ不足の懸念

**段階的実装による対策**:

1. **Phase 1-2**: 基盤整備（Rails CRUD、DB 設計）→ 既知技術で安定実装
2. **Phase 3**: コア機能（匿名性ロジック）→ セキュリティ検証が重要
3. **Phase 4**: React コンポーネント化 → MVP 完成後に段階的に導入
4. **Phase 5**: テスト・本番化 → 本格サポート

**不安な点と対応**:
- React 統合時期を MVP 後に設定し、基盤が安定してから導入
- Chartkick など外部ライブラリの学習は、実装時にドキュメント参照
- セキュリティ（匿名性ハッシング）は詳細設計段階で外部レビューを入れる
